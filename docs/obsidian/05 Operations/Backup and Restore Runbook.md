# Backup and Restore Runbook

**This is the design. the backup/restore implementation note (implemented separately) is what actually got
built from it — read that for real commands, real test evidence, and real
exit codes.** [[Database Operations Runbook]] already carries this as an
explicit checklist; this note is the fuller design behind it.

> [!warning] Implemented and tested — launch gate 10 is still OPEN
> `@telga/backup` exists, is tested against real synthetic training data (27
> cases in `tests/backup/`, 5 against the real compiled binary), and every
> design decision below — checkpoint-before-copy, isolated restore, the
> session and claim policies — is now real code, not aspiration. What is
> **not** yet true: it has never run against a chosen host, there is no real
> backup schedule, and no time-to-restore has been measured outside a local
> temp directory. See the backup/restore implementation note (implemented separately) "What remains open"
> and the acceptance checklist below.

## What is backed up

The single SQLite file (main database, plus its `-wal` and `-shm` files as
one unit — see below), which contains: the ledger, transactions, sessions,
device enrolments, audit events, recovery claims, and pending resolutions.
Nothing else needs backing up — there is no other durable state anywhere in
the system. Certificates and keys are **not** backed up alongside it; they
are deployment secrets with their own handling, never generated by Telga
(see [[Local Certificate Handling]]).

## How SQLite is safely copied

A raw file copy of a live WAL-mode database, taken mid-write, can capture the
main file and the `-wal` file at inconsistent points and produce a
**torn backup**. The safe sequence, design only:

1. Issue `PRAGMA wal_checkpoint(TRUNCATE)` against the live connection — the
   same checkpoint the driver already performs on clean shutdown (see
   [[Database Operations Runbook]] "WAL maintenance"). This folds the WAL back
   into the main file and truncates it, so a copy taken immediately after
   sees one consistent file rather than a file plus a separate WAL that must
   also be captured atomically.
2. Copy the main file only, after the checkpoint — no `-wal`/`-shm` file
   should exist immediately after a `TRUNCATE` checkpoint if nothing else
   writes in the gap.
3. If a checkpoint cannot be forced (e.g. the backup tool has no database
   access, only filesystem access), the fallback is SQLite's own **online
   backup API** or a filesystem-level snapshot that is atomic across all
   three files (main, `-wal`, `-shm`) — a plain `cp`/`rsync` of a live,
   uncheckpointed WAL-mode database is **not** safe.

## How active writes are quiesced

Design options, in order of preference:

1. **Checkpoint-and-copy without stopping the process** — `PRAGMA
   wal_checkpoint(TRUNCATE)` briefly blocks new writers until it completes,
   then releases them; the worker and POS keep running. This is the
   preferred approach for a training deployment, since stopping either
   process to back up daily is not something we want to build the habit of.
2. **A brief write pause**, if the checkpoint approach proves insufficient in
   practice — not designed further here because no evidence yet exists that
   it is needed.
3. **Full stop-the-world** (`SIGTERM` both processes, copy, restart) is the
   simplest to reason about and the safest starting point for the *first*
   backup implementation, even though it is not the eventual production
   shape. Prefer correctness on the first implementation over convenience.

## How ledger integrity is verified (of the backup itself)

After a backup file is produced, before it is trusted:

1. Open it **read-only**, in a separate, isolated process — never the live
   database file.
2. Run `driver.health()` against the copy: `integrity_check = ok`,
   `foreign_keys = 1`, `journal_mode = wal`, and — the decisive check —
   **ledger residual `0`**.
3. A backup that fails this check is not a usable backup. Alert, and keep the
   previous good backup as the current one.

## How append-only protections are checked

The append-only triggers on `ledger_entries` and `audit_events` are schema
objects, not application code — they travel with the database file itself.
Verifying them in a restored copy means confirming the triggers exist and
still refuse a mutation:

1. Query `sqlite_master` for the expected trigger names.
2. As part of a restore **test** (never against a real restore), attempt an
   `UPDATE` against a `ledger_entries` row and confirm it is refused — this
   is exactly what `tests/persistence/ledger-integrity.test.ts` already
   proves against a live database; a restore test should prove the same
   property survives a backup/restore round trip.

## How sessions and authentication data are handled

Sessions restore along with everything else in the same file — there is no
separate session store. Two consequences to design around, not yet resolved:

- A restored database's sessions may be **older** than the actual point of
  failure, so operators who signed in after the backup was taken will need
  to sign in again. This is expected and safe — sessions are stored as
  fingerprints only (see [[Authentication and Sessions]]), never raw tokens,
  so nothing sensitive leaks by restoring an old session table.
- A restore should **not** silently revive a session that was explicitly
  revoked after the backup point. This needs a documented operator step
  (communicate the restore point, ask affected operators to sign in again)
  rather than a code guarantee — flagged here as an open design question,
  not yet answered.

## How restore is performed into an isolated environment

Design, not implemented:

1. Restore **never** targets the live database path directly on the first
   attempt. It targets a fresh, isolated path (a temporary directory or a
   clearly-named `*.restored.sqlite` file).
2. Start neither the POS nor the worker against it automatically. A human
   confirms the checks below pass first.
3. Only after confirmation does the restored file replace the live one — and
   only with the live one moved aside, not deleted, so an operator can revert
   the restore itself if the new file turns out to be wrong.

## How migration version is checked

Read the applied-migrations table directly (the same mechanism
`packages/persistence/src/sqlite/migrator.ts` uses to decide whether the
worker/POS may start) and confirm it matches the version the running code
expects. A restored database from an older backup, on a newer code version,
is exactly the "unmigrated database" case the worker and POS already refuse
(exit `6`) — which is the correct, existing behaviour, not something new to
build.

## How residual is checked

Same check as any other health verification —
`driver.ledgerResidualMinor()` must be `0` on the restored copy before it is
trusted. See [[Database Operations Runbook]] "Procedure — ledger residual is
non-zero" if it is not.

## How recovery claims are checked

A restored database may contain claims with leases that have since expired
in wall-clock time (the backup is older than "now"). This is safe by
construction: `recovery_claims` leases are time-bounded, and an expired lease
is simply reclaimable by the next worker sweep — no special restore handling
needed, only confirmation (as a restore-test assertion) that a claim whose
lease has expired really is reclaimed rather than treated as still valid.

## How a restored worker is prevented from double-processing

This is the sharpest edge in the whole design. A restored database may show
a transaction as still `PROCESSING` when the *real* world (the mock provider,
in training) already resolved it after the backup was taken. Design answer:

- This is not a new problem — it is exactly what the recovery sweep already
  exists to handle (a transaction stuck past its pending deadline gets
  swept, checked against the provider's status, and resolved exactly once,
  idempotently). A restore does not need new logic here; it needs a restore
  **test** that proves the existing sweep behaves correctly starting from a
  deliberately "stale" restored state, not just from a normal stuck state.
- The claim lease (A37/R16) still applies unchanged after a restore — two
  workers (the pre-restore one, if somehow still running, and the
  post-restore one) cannot both resolve the same transaction, for the same
  reason they cannot on a live database.

## How the restore result is documented

Every restore — test or real — gets an [[Incident]] note (even a successful
test), recording: the backup point restored from, the migration version
found, the residual before and after, how long the restore took, and any
manual step an operator had to perform. Linked from
[[Database Operations Runbook]] and [[00 Home]], per the vault's "every fix
gets a note" rule.

## Acceptance criteria for closing launch gate 10

Updated against real, automated evidence (`tests/backup/`,
`tests/build/backup-restore-cli.test.ts`) — but the gate itself is **still
OPEN**. Passing tests against local temp-directory files is not the same as
a verified procedure on real infrastructure; the unchecked boxes below are
exactly that gap.

- [x] A backup script exists and checkpoints before copying — verified against a real (local) database file, not yet against a database on chosen host infrastructure
- [x] A restore script exists and restores into an isolated environment, never the live path
- [x] The restore test uses only synthetic training data
- [x] Ledger rows are preserved — verified by a whole-file SHA-256 checksum (stronger than a row-by-row diff) plus an exact row-count comparison per table
- [x] Residual is verified `0` on the restored copy
- [x] Append-only triggers are verified still active and still refuse a mutation on the restored copy
- [x] Claims are handled safely — **built stronger than originally scoped**: every claim is released unconditionally on restore (not only expired-lease ones), so no claim can be "stuck" in a restored copy at all
- [x] Sessions are handled safely — **built stronger than originally scoped**: every session is revoked unconditionally on restore, not only ones explicitly known-revoked
- [ ] No duplicate settlement occurs when **the worker actually sweeps** a restored database — partially verified: a test proves restore itself leaves a stuck transaction untouched (same state, same count, residual zero), but no test yet runs a real worker sweep against the restored copy end to end
- [ ] Time-to-restore is measured and recorded — not measured outside a local temp directory
- [ ] The restore result is documented in an [[Incident]] note — applies to a real operational restore, which has not happened

Until every box above is checked with real command output attached, gate 10
and assumptions A34/A41 stay **OPEN**. Full implementation detail:
the backup/restore implementation note (implemented separately).
