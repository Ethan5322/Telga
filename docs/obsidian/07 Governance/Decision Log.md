| D16 | 2026-08-20 | The provider call sits **between two units of work**, not inside one | A SQLite transaction is synchronous; holding one open across a network call would block every other writer for as long as the provider takes to answer, and the provider is the component that may not answer at all. | D17 | 2026-08-20 | A thrown provider call becomes `PENDING`, not `FAILED` | We do not know whether it delivered. Treating an exception as failure would release value on a sale that may have completed. | Claude Code |

| D19 | 2026-08-20 | A failure in the outcome unit of work **propagates**; it is not converted into a result | The instruction was explicit: do not catch errors and return success. The cost is a transaction that can stick at `PROCESSING`, recorded as open risk A31. | Founder |

| D20 | 2026-08-20 | The recovery sweep also sweeps `PENDING`, not only `PROCESSING` and `RESERVED` | `resolvePending` acts only when something calls it. | D21 | 2026-08-20 | `RESERVED` with no provider reference is **proof** the provider was never called | `createSale` transitions to `PROCESSING` before it submits. | D22 | 2026-08-20 | The pending clock starts when the transaction entered the in-flight state, not when the sweep noticed it | A transaction stuck for an hour must not receive a fresh grace period because a worker only just reached it. | D23 | 2026-08-20 | Recovery claims use a time-bounded lease, not a permanent lock | A worker that dies must not hold a merchant's money hostage. An expired lease is reclaimable; a permanent lock would need manual intervention exactly when nobody is watching. | Claude Code |

| D25 | 2026-08-20 | Sweeps are scheduled **fixed-delay**, from the end of the previous sweep, not fixed-rate | Fixed-rate scheduling degenerates into continuous execution the moment a sweep takes longer than its interval — the scheduler spends the rest of its life catching up on a backlog it can never clear. | D26 | 2026-08-20 | Database and schema failures are **fatal** to the worker; provider failures back off | Retrying into a broken connection or a wrong schema helps nobody and hides the fault. | D29 | 2026-08-20 | A shutting-down worker releases **only its own claims**; everything else is left to expire | Touching another worker's claim would let two workers act on one transaction. | D107 | 2026-08-31 | **The APK handed to a merchant is release-signed with Telga's own key and carries a v1 signature the tooling says is unnecessary.** `npm run mobile:package` produces it. | A debug APK was refused by the owner's phone with "App not installed". **The build was not at fault** — it is signed, architecture-independent, zip-intact, minSdk 24, and installs and launches on Android 14 (verified on an emulator: `Success`, MainActivity resumed, no fatal logs). What a debug build *does* carry is `debuggable=true` and the universally-known Android debug key, which Play Protect blocks after "Installing…". **What was rejected:** shipping debug builds to merchants at all. **The v1 signature:** AGP drops v1 above minSdk 23 and apksigner refuses it below `--min-sdk-version 21`; both are correct by specification, and it is added anyway because some OEM package managers have been fussier than stock Android, and the cost is a slightly larger file against a merchant who cannot install Telga and is told nothing. **Not yet proven:** the owner's phone still refused the release build, and the remaining causes — Play Protect, a conflicting package, a broken transfer, a device policy — cannot be told apart without the device. `npm run mobile:diagnose` prints the real code. | D108 | 2026-09-05 | **The cloud target is one Railway service with a persistent volume, keeping SQLite. The PostgreSQL/Supabase migration is deferred, and nothing has been provisioned.** Current environment: **local development only**. | The owner asked for Supabase + Railway + Vercel. A vault compliance scan found that plan already documented as deployment-blocking ([[Vercel Deployment Limits]], accepted; R30; A56), and inspection confirmed why. **Vercel cannot host either front end:** the POS and the console are Node HTTP servers rendering HTML server-side with database-backed sessions, not static bundles — there is no web root to publish. **The Postgres swap is larger than the vault claimed:** [[Vercel Deployment Limits]] said a second `LedgerDriver` implementation would change "nothing else", but `driver/types.ts` has *zero* Promise-returning methods and its unit of work is `transaction<T>(work: () => T): T`, a synchronous callback. Every Node Postgres client is async, so the swap is an async refactor across ~80 files and 21 transaction call sites, plus re-proving the claim lease (A37/R16) on a new engine, plus resolving D103 one-database-per-shop against a single shared instance. That is a project needing its own plan and its own approval, and it is **not justified before a provider agreement exists**. **What was chosen instead** is Category 2 of [[Deployment Target Evaluation]]: one service, one volume, one replica, SQLite unchanged, the worker and the POS sharing one file because `recovery_claims` only prevents double resolution when they do. **Explicitly not approved:** the PostgreSQL/Supabase migration, a Railway subscription, and `telga.et`, which has not been purchased (A89) and must not be configured. | Founder |
| D109 | 2026-09-05 | **`--trust-proxy` accepts a CIDR range, and Telga ships no built-in range for any hosting platform.** A zero-length prefix (`0.0.0.0/0`, `::/0`) is refused at startup, and an untrusted forwarding hop is reported once as `PROXY_PEER_OBSERVED`. | A platform terminator draws its address from an internal pool, so an exact address cannot be configured for one — and matching was exact-string only, which is why the platform question looked unanswerable. A range is still an **explicit** statement about who is trusted, so this widens what can be *expressed* without widening what is trusted by default: D45's rule that there is no trust-all setting is preserved by refusing `/0` in the parser, where it cannot be forgotten. **No platform range is hardcoded.** Railway's own documentation does not publish the address its edge forwards from; a community post reports `100.0.0.0/8`, which is unverified and wider than the `100.64.0.0/10` carrier-grade NAT block, so it would include publicly routable space. Guessing it would be exactly the "wrong answer arriving looking like the right one" that the whole trusted-proxy design exists to prevent. So Telga **observes and reports** the hop instead, once per address, and the operator verifies and configures it. Observing never trusts. A malformed entry is refused at startup rather than silently matching nothing, because a range that matches nothing looks identical to a working deployment until the first sign-in fails. | Claude Code |
| D110 | 2026-09-06 | **The Railway deployment is a training deployment, and is recorded as one everywhere it could be misread.** No custom domain, no merchant access, a Railway-generated address only, `TELGA_MODE=TRAINING` refused any other value, and `TELGA_RECIPIENT_SALT` set in Railway so the public fallback constant is never the salt in use. | Asked directly whether Telga Pay and the voucher flow are regulated features being switched on by the back door. They are not, and the check was worth making rather than answering from memory. **Telga Pay** is gated by `card.simulated`, a flag deliberately kept distinct from `payments.acceptance` — the simulator implements the same `CardReader` and `PaymentProcessor` ports a certified terminal will, decides from the card number, marks every result `simulated: true`, and a search of `services/provider-adapters/` finds no `fetch`, no HTTP client and no socket: nothing there can contact anything. The Visa and Mastercard wordmarks on screen are labels carrying the string *"shown as training examples only. No real card network is connected."* **Vouchers** are gated by `product.data` (D72, training-scoped) and cannot carry value: every PIN is prefixed `TRAIN-`, every dial string `*000*`, and the network is named `NETWORK_A` rather than a carrier. **Every regulated capability is off** — `money.live`, `wallet`, `payments.acceptance`, `cash.in_out`, `lending`, `remittance`, `settlement.independent`, `funding.submission`, `product.electricity`, `bills.general`, `vending.offline` — enforced in three layers: `isEnabled` for the UI, `routeBlockedBy` answering `404` before authentication or any body read, and `findRoleCapabilityLeaks` for roles. The fourth layer, deployment exclusion, is **still not implemented**, and the module says so rather than claiming it. **The honest caveat:** a real URL with real uptime invites the description "live". It is not. Recorded as A98. | Founder |
| D111 | 2026-09-06 | **`TELGA_RECIPIENT_SALT` is a required secret for the Railway training deployment, and the committed fallback must never be the salt in use.** | The worker falls back to the literal `cli-salt-not-a-production-secret` when the variable is unset, and that literal is public in this repository — so a digest made with it is recomputable by anyone who can read the repo, which is the rainbow-table exposure [[Security Model]] introduced the salt to close. Setting the variable costs nothing and removes a published constant from the security boundary. **What this decision does not fix, and does not pretend to:** the POS ignores the variable entirely and salts per process with `randomUUID()`, deliberately, on the grounds that the training build stores no real recipient. So the two processes salt differently and the POS's salt changes on every redeploy. That is tolerable while every recipient is simulated and nothing compares digests across processes; it is not tolerable the day a real recipient is stored, and it is recorded as A97 rather than quietly carried. | Founder |
